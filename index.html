Arora Classes — Website Architecture

Design document for the website of Arora Classes, a Class 9–12 coaching centre in Kitchlu Nagar, Ludhiana. The site answers the questions parents currently ask by phone, and lets the owner post updates without touching code.

The problem this solves

Arora Classes receives 10–15 enquiry calls a day. Most arrive during class hours and go unanswered, and the ones that connect ask the same four things: batch timings, fees, seat availability, and faculty. Parents who can't get through call the next centre. Published information removes most of those calls; an enquiry form captures the rest.

How to read the diagrams

  • Dashed rectangles are trust boundaries. Anything inside the client tier is public and can be read by any visitor; anything inside the application tier is private to the server.
  • Solid arrows are requests or calls, labelled with the protocol and what travels over them.
  • Dashed arrows are direct asset fetches that bypass the application.
  • Monospaced labels such as POST /api/enquiry are the exact endpoint involved.

Frontend Layer

Ten routes in total. Six are public and statically generated, so they load from the CDN edge with no server work. Four are admin routes, rendered dynamically and never cached. Only two pages in the whole application send data anywhere.

Figure 2 — Routes, rendering mode, and the call each route makes.

Rendering strategy

RouteModeWhy
Home, Courses, Fees, FacultyStaticContent changes only on redeploy; served from CDN
UpdatesStatic + 60s revalidateNew posts must appear without a rebuild
ContactStatic shell, client formPage is fixed; only the form is interactive
All /admin/*Dynamic, uncachedPrivate data must never be cached
No global state library. Server components fetch their own data and the two forms hold local state. Adding Redux or similar here would be overhead with no benefit.

Validation rules

const EnquirySchema = z.object({
  name:          z.string().min(2).max(60),
  phone:         z.string().regex(/^[6-9]\d{9}$/),   // Indian mobile
  student_class: z.enum(['9','10','11','12','other']),
  message:       z.string().max(500).optional(),
  website:       z.string().max(0),                  // bots fill this
});

const UpdateSchema = z.object({
  title:     z.string().min(3).max(120),
  body:      z.string().min(1).max(4000),
  image_url: z.string().url().optional(),
  file_url:  z.string().url().optional(),
});

Why stage 5 is separated. Email delivery is the least reliable step in the system. If Resend is unreachable the enquiry row already exists, so the parent still sees success and the owner finds the enquiry in the admin inbox. Storing and notifying are two different guarantees.

Database Layer

Two tables and one bucket. There is deliberately no relationship between the tables — they serve two unrelated flows. Batches, fees and faculty are not stored here at all, because the owner does not edit them.

Figure 4 — Tables, bucket, and where the rest of the content lives.

Schema — DDL

create table updates (
  id            uuid primary key default gen_random_uuid(),
  title         text not null,
  body          text not null,
  image_url     text,
  file_url      text,
  is_published  boolean not null default true,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

create index updates_public_idx
  on updates (created_at desc)
  where is_published = true;

create table enquiries (
  id            uuid primary key default gen_random_uuid(),
  name          text not null,
  phone         text not null,
  student_class text not null,
  message       text,
  status        text not null default 'new'
                  check (status in ('new','contacted','closed')),
  created_at    timestamptz not null default now()
);

create index enquiries_status_idx on enquiries (status, created_at desc);

-- block the public anonymous key entirely; all access goes

Deployment Layer

One repository, one deploy. Pushing to a branch produces a preview URL; merging to main promotes it to production. Rollback is a single action, which matters the night before a submission.

Section 6

Key Decisions

Each row is a choice that could reasonably have gone the other way.

DecisionRationaleTrade-off accepted
Monolith, not separate frontend and backendOne deploy, no CORS, no second hostFrontend and backend scale together
Serverless functions, not a persistent serverZero cost at this traffic, no administrationCold starts on the first request
Batches and fees in code, not in the databaseOwner only needs to edit updates; removes three tables and three admin screensA fee change needs a redeploy
Enquiries stored and emailedEmail delivery is unreliable; the row is the source of truthTwo places to check
Files in object storage, not in PostgresDatabases handle binaries poorly; CDN serves them betterTwo systems to keep consistent
RLS enabled with no policiesStricter and simpler than writing row rules for a single adminAll access must go through the server
Email notification, not WhatsApp APIWorks on day one without business-number approvalOwner checks email less often than WhatsApp
Section 7

Roadmap

Five phases. Each one leaves the system deployable and useful — stopping at phase three still yields a working product rather than a broken one.

PhaseScopeValue delivered
1Static site with all fixed contentParents can find timings and fees without calling
2Enquiry form: validation, persistence, emailMissed calls become captured enquiries
3Login and text-only updatesOwner publishes notices himself
4Image and PDF attachments on updatesTest schedules and notices shared as files
5Admin enquiry inbox with statusNo enquiry is followed up twice or forgotten

How success is measured

  • Baseline, before launch: ask the owner roughly how many enquiry calls arrive daily and how many are missed during class hours.
  • After two weeks live: count enquiries received through the form.
  • Even "six enquiries in two weeks that would previously have been missed calls" is a real result — and measuring it is what separates a project from a demo.
